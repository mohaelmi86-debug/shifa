## 2. Multi-tenant isolation

**PASS**

### Test logique d'isolation

| Acteur | Cible | Résultat attendu | Résultat après P0.6 |
|--------|-------|-----------------|---------------------|
| ORG_ADMIN_A | ORG_A data | ALLOW | ✅ ALLOW — `is_org_admin_for(ORG_A)` = TRUE |
| ORG_ADMIN_A | ORG_B data | DENY | ✅ DENY — `is_org_admin_for(ORG_B)` = FALSE |
| PROFESSIONAL_A | ORG_A data | ALLOW (via belongs_to_org) | ✅ ALLOW |
| PROFESSIONAL_A | ORG_B data | DENY | ✅ DENY — `belongs_to_org(ORG_B)` = FALSE |
| PATIENT_A | ORG_A data | ALLOW (own records) | ✅ ALLOW — `user_id = auth.uid()` |
| PATIENT_A | ORG_B data | DENY | ✅ DENY |
| PLATFORM_ADMIN | ORG_A | ALLOW | ✅ ALLOW — `is_platform_admin()` = TRUE |
| PLATFORM_ADMIN | ORG_B | ALLOW | ✅ ALLOW — `is_platform_admin()` = TRUE |

### Mécanisme de la correction

```
AVANT (DANGEREUX):
is_org_admin() → TRUE si role IN ('org_admin', 'platform_admin')
→ ORG_ADMIN_A peut lire/modifier les données de ORG_B

APRÈS (SÉCURISÉ):
is_org_admin_for(organization_id) → TRUE seulement si
  (role = 'org_admin' AND user_profiles.organization_id = target_org_id)
  OR role = 'platform_admin'
→ ORG_ADMIN_A ne peut accéder qu'à ORG_A
```

## 5. audit_logs

**PASS**

### Problème identifié (P0.5)

```sql
-- AVANT (DANGEREUX — 20260812200000_rls_all_modules.sql):
CREATE POLICY "audit_logs_insert" ON public.audit_logs
  FOR INSERT WITH CHECK (true)
-- → N'importe quel utilisateur authentifié peut écrire n'importe quoi
```

### Correction appliquée (P0.6)

```sql
-- APRÈS (SÉCURISÉ):
CREATE POLICY "audit_logs_insert" ON public.audit_logs
  FOR INSERT WITH CHECK (
    auth.uid() IS NOT NULL
    AND (
      user_id = auth.uid()
      OR (organization_id IS NOT NULL AND public.is_org_admin_for(organization_id))
      OR public.is_platform_admin()
    )
  );
```

**Règles d'écriture des audit_logs :**

| Acteur | Peut écrire | Condition |
|--------|-------------|-----------|
| Utilisateur authentifié | Ses propres entrées | `user_id = auth.uid()` |
| org_admin | Entrées de son org | `is_org_admin_for(organization_id)` |
| platform_admin | Toutes entrées | `is_platform_admin()` |
| Service role (edge functions) | Toutes entrées | Bypass RLS — correct |
| Utilisateur non authentifié | AUCUNE | DENY |
| Utilisateur d'une autre org | AUCUNE | DENY |

## 9. NULL data

**ANALYSIS**

### kiosk_checkins.patient_user_id

**Backfill effectué** via la relation confirmée :
```
kiosk_checkins.patient_id → public.patients.id → public.patients.user_id
```

- Relation confirmée par le schéma (FK existante)
- Backfill conditionnel : uniquement les lignes où `patient_user_id IS NULL` ET `patients.user_id IS NOT NULL`
- Aucune donnée inventée — uniquement reconstruction de relation existante

### shifa_ids.organization_id

**NULL conservé — aucun backfill**

Raison : La table `shifa_ids` ne possède pas de chemin de jointure fiable vers `organizations` autre que la colonne `organization_id` elle-même. Il n'existe pas de colonne `issuing_organization_id` ou de FK intermédiaire permettant de déterminer avec certitude quelle organisation a émis chaque SHIFA ID.

**Recommandation** : Renseigner `organization_id` à la création via le workflow kiosk/admin. Les lignes NULL existantes représentent des IDs émis avant l'introduction de cette colonne.
